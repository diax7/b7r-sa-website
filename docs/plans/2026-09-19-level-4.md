## PR 4a: the inbox

- **`messages` collection** (the contact form's submissions): `name`, `phone`, `email`,
  `inquiry` (the form's select), `message`, `locale`, `page` (the path the form was on),
  `utm` (source, medium, campaign), `status` (`new` · `following` · `handled`), `notes`
  (internal, textarea), `emailed` (whether the notification e-mail left). `/api/contact`
  stores the row **before** sending the e-mail, through the local API with access overridden
  (the route is the only writer; anonymous REST creates are refused); an e-mail failure
  leaves the row with `emailed: false` and the admin shows it. No localized fields.
- **Access:** admins and editors read and update (status, notes); only admins delete;
  nobody outside. `tests/access.test.ts` gains the outsider's rows.
- **Where in the panel:** a section **Inbox** («الوارد») under the **Site** group, first in
  the group, holding `messages` and, from PR 4b, `bookings` (the engine's section under Blog
  is the precedent); its own icon, the two entities' icons and labels in the registry. No
  sixth group and no sixth hue (CTO, 2026-09-19: every free hue sits beside a meaning colour
  or the accent; the "daily task" signal is the red badge and the dashboard card, rule 14).
- **Actions on a message** (`beforeDocumentControls` after the sentinel; through `ApiAction`
  where a write happens): «رد على WhatsApp» opens `wa.me/<phone>?text=<greeting in the
  message's locale>`; «رد بالبريد» opens `mailto:` with a subject; «تمت المعالجة» sets
  `status: handled` (an admin-only JSON route through `adminOnly()`). The list shows the
  status as a pill with its word (`StatusCell`: `new` blue "needs you", `following` amber,
  `handled` green; three glossary rows), `defaultColumns` name · inquiry · status · created.
- **Personal data rules** (the first rows holding a stranger's name, phone and e-mail): no
  personal field in any log line (a failure names the row id, never the phone or the
  message); editors update `status` and `notes` only (field-level `access.update` refuses an
  editor rewriting the merchant's fields); nothing is deleted automatically, an admin deletes
  (RUNBOOK and BRD §11.1 say so); the outsider test proves the public key reads, lists and
  updates nothing on the collection.
- **Badge and dashboard:** a sidebar badge kind `inbox` (new messages, red when any; from
  PR 4b also today's bookings) with its sentence in both trees; a dashboard **Inbox card**
  (new messages with the first line of the newest three, a link to the list) in the content
  column. The hand line stays the score's guidance (ADR-059), nothing added there.
- **Words:** every label, description, status word and toast in both trees through the
  glossary (rows: message, inquiry, inbox, status words); descriptions under the 140 cap.
- **Tests:** `messages.test.ts` (the route stores then sends; a failed send keeps the row;
  the honeypot stores nothing; UTM and page captured), access, config census (group, icons,
  columns, status pill), badge reader, dashboard card; e2e: a submission on `/contact`
  appears in the inbox with its pill, the WhatsApp action's href, mark handled, the badge
  count, axe on the list and the document in both languages at 1440 and 390.
- **Docs:** ADR-061 (the inbox, the section under Site, the store-then-send rule, the
  personal-data rules), design system (the section row), RUNBOOK (reading the inbox; what
  `emailed: false` means; deletion is an admin's act), BRD §11.1 amended (no assignee; the
  subscribers list deferred to a future block), the checklist.

## PR 4b: bookings of our own

- **Settings:** a global **`booking`** («الحجز») under Site beside Home and Site settings
  (a place on the site with its own switch and its own revalidation, not a sixth tab of the
  panel's largest form): `enabled` (`EnabledSwitch`; off keeps the contact card's WhatsApp
  behaviour, BRD §6.9 and §11.2), `title` (bilingual: «استشارة مجانية، 30 دقيقة»),
  `durationMinutes` (30), `bufferMinutes` (10), `noticeHours` (24), `horizonDays` (30),
  `maxPerDay` (4), `hours` (rows: `day` Sunday–Saturday, `from`, `to` in Riyadh time; the
  seed: Sunday–Thursday 10:00–18:00), `closedDates` (rows: a date and a bilingual reason),
  `hostEmail` (the Workspace user whose calendar is read and written; the delegated
  `subject` is always this value, never one from a request). `site-settings.bookingUrl` is
  deleted (one additive migration keeps the column; the field goes). Every field described
  under the 140 cap.
- **Connection kind `google-calendar`** (`speaks: 'service'`, secret `serviceAccount`): the
  same key file as Search Console, pasted again on its own row (one row per service,
  ADR-047); `signJwt` gains an optional `subject` (the delegated user) and the kind asks the
  **two narrow scopes** the feature uses, `https://www.googleapis.com/auth/calendar.events`
  (insert, patch, delete) and `https://www.googleapis.com/auth/calendar.freebusy`, never the
  whole `calendar` scope (delegation lets the key act as any user on b7r.sa for the scopes
  granted); the Test button reads free/busy for today, which also proves the delegation.
  Dhia's side, once: enable the Calendar API on the service account's Cloud project, and in
  the Workspace Admin console add domain-wide delegation for the service account's client
  id with those two scopes. The RUNBOOK says what the delegation means and that a leak is a
  key rotation in the Cloud console, not a row edit.
- **`bookings` collection:** `name`, `email`, `phone`, `locale`, `start`, `end` (UTC;
  shown in Riyadh), `status` (`booked` · `rescheduled` · `cancelled` · `completed`),
  `meetLink`, `googleEventId`, `calendar` (`synced` · `failed` · `off`), `page`, `utm`,
  `notes`, `reminded24h`, `reminded1h`. No token column: the manage link carries a signed
  token (`internalToken('booking-manage')` over `{ id, exp }`, `lib/internal-token.ts`);
  the route verifies the signature, then reads the row and decides by its `status` and `end`
  (a cancelled booking refuses every action; expiry `end + 1 day` from the row, never from
  the token). A partial unique index on `start` where `status` is not `cancelled` (one
  raw-SQL additive migration; a generated drizzle diff never carries it, so it is created
  and dropped by hand, said in the migration) makes a double booking a database refusal, not
  a race; the in-write re-check answers the 409 in the person's language first and maps
  Postgres `23505` to the same 409. **The grid rule** that makes the index sufficient: every
  booking sits on the grid the slot generator produces (`from` plus multiples of
  `duration + buffer`); the route refuses a `start` that is not in the day's computed free
  slots (400), never an arbitrary time, so two rows with different `start` cannot overlap.
  The same personal-data rules as `messages` (no personal field in a log line, editors
  update status and notes only, an admin deletes, the outsider test).
- **Slots** (`modules/bookings/slots.ts`, pure): from the global's hours, the closed dates,
  the notice and the horizon, minus the day's bookings (with the buffer on both sides) and
  minus the host calendar's busy blocks (`freeBusy`, cached 60 s per day); the day's
  `maxPerDay` caps it; Riyadh arithmetic with no DST (`lib/riyadh.ts`). `GET
  /api/bookings/slots?date=YYYY-MM-DD` answers the day's free starts (public, cached 60 s,
  rate limited) and refuses a date outside today..`horizonDays` (400), so the host's pattern
  cannot be scraped for months.
- **Booking:** `POST /api/bookings` in the contact route's order (JSON + same origin → zod
  → honeypot → rate limit → Turnstile) → the slot re-checked inside the write → the row →
  the Google event on the host's calendar (`conferenceDataVersion=1`, `createRequest` with a
  fresh `requestId` and `hangoutsMeet`, the merchant as an attendee, `sendUpdates: 'none'`,
  since our e-mails carry the link) → `meetLink` stored → the merchant's confirmation e-mail
  in their language (the time in Riyadh, the Meet link, a calendar file attached, the manage
  link) and Dhia's notification e-mail. If Google refuses, the booking stands with
  `calendar: failed`, Dhia's e-mail says so, and a job retries three times an hour apart;
  the merchant's e-mail says "the link follows" and a second e-mail carries it.
- **Manage:** `/book/manage?token=…` (both languages): the booking, «غيّر الموعد» (a new
  slot from the same picker under the same notice rule as a new booking; the Google event
  patched, both e-mails again) and «ألغِ الحجز» (allowed until `start`; status `cancelled`,
  the event deleted, both e-mails). `GET /api/bookings/ics?token=` serves the calendar file.
  One signed link serves the merchant for the booking's life; a cancelled or past booking
  refuses every action.
- **The sweep:** a job every 15 minutes, idempotent by the flags, with **open-ended
  windows** so a late runner sends late rather than never: `start <= now + 24 h AND start >
  now + 1 h AND NOT reminded24h` → the 24-hour e-mail (merchant and Dhia) and the flag;
  `start <= now + 1 h AND start > now AND NOT reminded1h` → the 1-hour e-mail and the flag;
  `end < now AND status IN (booked, rescheduled)` → `completed` (no manual «اكتمل»); and
  the Google retry for `calendar: failed` rows (three tries an hour apart). The cron rides
  the dashboard's jobs list. **WhatsApp:** a button on the booking («ذكّر على WhatsApp»)
  opens `wa.me` with a prefilled reminder in the merchant's language; nothing automatic (the
  Business API is a future block).
- **Site:** `/book` and `/en/book` (the §4.11 copy from the copy bank; the BRD's route), and
  the contact page's booking card opens the same picker inline; one client island
  (`modules/bookings/picker`), loaded near the viewport like the newsletter island: a month
  strip → the day's slots in Riyadh time with Western digits → name, phone, e-mail, note →
  the confirmation screen with the Meet link and the calendar file. JS budget: the island
  stays out of the home bundle; `/contact`'s budget is measured. Sitemap, metadata, a `WebPage`
  JSON-LD only, both languages, axe.
- **Inbox:** `bookings` in the Inbox section with the status pill (`booked` green,
  `rescheduled` amber, `cancelled` red, `completed` neutral) and the WhatsApp reminder
  action; the badge counts today's bookings; the dashboard Inbox card lists the next three.
- **Tests:** `slots.test.ts` (hours, buffer, notice, horizon, closed dates, max per day,
  busy blocks, the day boundary in Riyadh, an empty day), the route order, the double-booking
  refusal (two concurrent writes, one 409), the Google client against recorded bodies (event
  created, Meet pending then present, a refusal), the e-mails' contents in both languages
  with the calendar file, the reminder window arithmetic, the manage token (hash, expiry,
  a wrong token), access; e2e: `/book` in both languages books a slot on the review server
  with the Google client mocked (a `mock` calendar connection, refused in production like
  the AI mock, with a `fail` flag in its config that drives the `calendar: failed` path: the
  booking stands, Dhia's mail says so, the second mail carries the link after the retry), the
  confirmation, the manage page's reschedule and cancel, an off-grid `start` refused, a
  reschedule inside the notice refused, the inbox row and its pill, the `/contact` JS budget
  asserted with the island out of the first paint, axe at 1440 and 390 both languages.
- **Docs:** ADR-062 (bookings of our own: why not Cal.com, the delegation, the Meet link,
  the double-booking index, the token), RUNBOOK (the Workspace setup steps, what
  `calendar: failed` means, the retry), BRD §11.2 rewritten, §12.4 the checklist rows
  (Calendar API enabled, delegation added, `hostEmail` set, a real test booking), the
  design system (the picker is a site component under §3.10).

## PR 4c: Umami on the dashboard

- **Connection kind `umami`** (`speaks: 'service'`, secret `apiKey`, base URL fixed
  `https://api.umami.is/v1` for Cloud, a `baseUrl` for `umami.b7r.app`): the API key; the
  website id comes from Site settings → Analytics (already there). The Test button calls
  `GET /websites/{id}/stats` for yesterday.
- **The pull:** the nightly job (`visibility/pull.ts`) gains the `umami` source: one
  `stats` call per missing day (visitors, page views, visits, bounces, total time) into
  `metrics` (`source: 'umami'`), 90 days back on the first run, then the last two days each
  night (Umami finalises late hits).
- **The dashboard:** the visits card's tile shows Umami's visitors for the period beside our
  landings ("3,900 visitors · 4,881 landings"), the card's table gains a "people" row
  (visitors, page views, average time) for 7/30/90 days from `metrics`; no Umami row when the
  connection is missing (the card reads as today). The Traffic page is untouched. Day
  arithmetic: `startAt`/`endAt` in milliseconds on **Riyadh** day boundaries, the same
  boundary the other `metrics` sources use, so the card never sums two different days.
- **Tests:** the parser over a recorded body, the pull's day arithmetic, the connection
  test, the dashboard reader with and without the source; e2e: the visits card with a
  seeded metric row in both languages.
- **Docs:** ADR-048 amended (Umami's numbers join the counter; GA4 stays in GA), RUNBOOK
  (the API key from Umami Cloud → Connections), the checklist row.
